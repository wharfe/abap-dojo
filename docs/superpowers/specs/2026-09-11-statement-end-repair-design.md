# ピリオド抜け・行末セミコロンに直し方を出す（#67 の残り 2 形）

Gate1（grilling による軽量版）。2026-09-11 に Q1〜Q5 をユーザーが確定。Q6 は Gate2 1 周目の指摘 H1、Q7 は Gate2 3 周目の
指摘 H-B を受けて同日に追加で確定。**2026-09-12、Gate2 新周回 1 周目の指摘 H1（同じ根が 3 回目）を受けて、手段を替えた**
— Q8〜Q13 を追加し、Q6 / Q7 は残したうえで**守るものを差し替えた**。Q1〜Q5 は変えていない。

## 何を解決するか

#69 の出荷後（2026-09-09..10）、`syntax_statement = WRITE` の `parser_error` 31 件のうち、
直し方のヒントが出たのは二重引用符の 4 件だけだった。残りの大半は #67 が見つけた未対応の 2 形
— **文末のピリオド抜け**と**行末のセミコロン**。どちらも abaplint のメッセージは
`Statement does not exist in the configured ABAP version` で、何を直せばよいかを言わない。

あわせて #75 を同じ PR で直す。再パースによる探索が重い貼り付けでワーカーを塞ぎ、
**本物の構文エラーが 20 秒のウォッチドッグで `stalled`（エンジンが応答しない）として表示・計測されうる**。

## 既にある仕組みを探したか

探した。abaplint はこれらの `parser_error` に修正案を付けない（`getDefaultFix()` /
`getAlternativeFixes()` はどちらも `null`、2026-09-11 実測）。ピリオドやセミコロンを扱う
ルールも無い（`ArtifactsRules` のキーを検索）。したがって #69 の方式 —
**行の見た目で判断せず、書き換えた版を abaplint に再パースさせ、判定が良くなった書き換えだけ採る** —
をそのまま再利用する（`src/workers/syntaxRepair.ts`）。

## 手段を替えた理由（2026-09-12）

Gate2 で **「上限では探索の時間を抑えきれない」という同じ根の指摘が 3 回**出た（1 周目 H1・3 周目 H-B・新周回 1 周目 H1）。
周回の規則により実装ではなく仕様へ戻り、**その制約は目的由来か手段由来か**を問い直した。

- **目的**: 本物の構文エラーを `stalled` にしない
- **手段**（＝崩してよかったもの）: 判定と探索を、同じワーカーの**同じ 1 通の返信**で返す

探索が 20 秒の窓の中にある限り、探索の所要時間が `outcome` の正しさを支えてしまう。だから上限が時間を保証できないことが
毎回 high になった。手段を替えて探索を窓の外に出せば、その保証が要らなくなる。

### 前提の実測（2026-09-12、Node）

| 確かめたこと | 結果 |
|---|---|
| 先に投げた `postMessage` は、同じワーカーが焼き続けていても親に先に届くか | **届く**。判定は 2.5 ms で親に到着し、そのあとワーカーは 1,699 ms 占有し続けた（`worker_threads`、16 kB の `x⏎` を 1 回パース） |
| `parseAsync` はイベントループに譲るか | **譲らない**。1,502 ms のパース中にマクロタスク 0 回（マイクロタスク 3 回）。→ 探索中は同じワーカーの `lint` が 1 件も動けない |

## 決めたこと

## プロトコル（Q8 / Q9）

### 今

```
parse ──→ 探索 ──→ 返信 1 通
└────────── 20 秒の窓 ──────────┘      ← 探索が窓の中にいる
```

探索が遅い形では返信が窓の外に落ち、`App.tsx` の requestId ガードに弾かれる。画面にも GA4 にも `stalled` が残る。

### これから

```
失敗側:  parse → [transpile-error を送信] → 探索 → [syntax-hint を送信]
成功側:  parse → transpile → [transpile-result を送信] → 探索 → [silent-loss を送信]
例外時:  parse/transpile が投げた → [transpile-error(transpile) を送信] → [silent-loss(completed:false) を送信]
         └── 20 秒の窓 ──┘                                   ← 窓に入るのは元のパース（＋トランスパイル）だけ
```

- **成功側はいまより速くなる。** 探索はいまパースとトランスパイルの間に挟まっていて（`abaplintWorker.ts:130`）、
  成功する Run 全部が探索を待ってから実行を始めている。後ろへ移すと実行がその分早く始まる
- **「どちらの出口でも `silent_loss` の答えがある」という今の性質は保つ。** 探索をトランスパイルの後ろへ移しても、
  トランスパイルが投げた経路でも追いかけの 1 通は必ず送る（`completed: false`）
- **メッセージ型**（`src/types/messages.ts`）:
  - `{ type: "syntax-hint"; requestId: string; repair?: SyntaxRepair }`
  - `{ type: "silent-loss"; requestId: string; completed: boolean; loss?: SilentLoss }`
  - `completed` は今の `silentLossChecked` と同じ意味。`false` なら `silent_loss` を送らない（`none` と区別する既存の約束）
- **Validator モード（`handleValidate`）は触らない。** 別の入口で `handleTranspile` を通らず、`silent_loss` も
  `syntax_repair` も出していない（`validate_result` はそれらを持たない）。Playground が量を持っているという既存の
  スコープ判断のまま（`CLAUDE.md` Analytics 節）。ここを変えると Gate2 の対象が倍になるだけで、測れるものは増えない

### 親側（`App.tsx`）

1. **判定が来たら即表示する。** 失敗側は今までどおり `endRun` を呼ぶ（`isRunning` 解除・エラー表示・ウォッチドッグ解除）
2. **`run_result` は追いかけの 1 通が来るまで送らない。** `endRun` は payload を作るところまでやって溜める。
   **`duration_ms` は `endRun` が呼ばれた時点で確定させる**（送信を遅らせても数字の意味を変えない）
3. 追いかけが来たら `syntax_repair` / `silent_loss` を差し込んで送る。**来なければ 20 秒で、無しのまま送る**
4. **次の Run が始まったら、溜まっている分をその場で（無しのまま）送る。** `run_click` と `run_result` の 1:1 を維持する
5. **追いかけメッセージのガードは `playgroundRequestIdRef` ではなく専用の ref にする。**
   `endRun` は #50 のために `playgroundRequestIdRef` を空にするが、それは「遅れて来た `transpile-result` が古い JS を
   サンドボックスへ渡さない」ためのもの。追いかけメッセージは実行を始めないので、別の ref で相関させてよく、そうしないと
   追いかけが必ず捨てられる
6. **ヒントの表示は、その Run のエラーがまだ画面に出ているときだけ**継ぎ足す
7. `silent_loss` のヒント表示（`silentLossHint_` のソース一致方式）は**変えない**。あれは既に
   「Run の返事がユーザーの編集より後に届く」場合を想定して作られている（`App.tsx:133-145`）

## 候補の作り方（2026-09-11 の実測に基づく）

候補は**元のエラーの行範囲**（`getStart().getRow()`〜`getEnd().getRow()`）からだけ作る。

- **semicolon**: 範囲内で `;`（後ろの空白・`\r` は可）で終わる行の `;` を `.` に置き換える。
  1 行ずつ + 全エラーの該当行をまとめて
- **missing_period**: エラーの**終わりの行**の末尾に `.` を足す（始まりの行に足すと、
  複数行にまたがる文で 1→2 に悪化する）。まとめ候補は範囲内で `.` `,` `:` で終わらない
  空でない行すべてに足す（`,` `:` を除くのはチェーンの継続行を壊さないため）
- **まとめ候補の「対象」**は、書き換えた行を含むエラーだけ。別の行の無関係なエラーは書き換えても
  必ず残るので、対象に入れると本物の修正を捨てる（Gate2 M1。`WRITE 'a'` ⏎ `WRITE 'b'` ⏎
  `WRITE 'c'.` ⏎ `WRTE 'd'.` が黙っていた）

| 入力 | 期待 |
|---|---|
| `WRITE 'hello'`（最終行 / 途中 / IF の中） | `missing_period`、行番号あり |
| `WRITE: 'a',` ⏎ `'b'`、`lv = to_upper(` ⏎ `'a' )`（複数行の文の末尾） | `missing_period`、終わりの行 |
| 2〜3 行連続のピリオド抜け | `missing_period`、行番号なし |
| `WRITE 'a';` / 2 行連続 / CRLF | `semicolon`（1 行は行番号あり / 2 行は行番号なし） |
| `WRTE 'a'.` / `console.log('a')` / `console.log('a');` / `const x = 5;` / `let x = 1` ⏎ `console.log(x)` / `print('a')` / ピリオド抜け + 別行の綴り間違い / `DATA lt TYPE string_table.` | **ヒントなし** |
| `WRITE 'a' " note`（行末コメントに隠れたピリオド抜け） | **ヒントなし — 届かない限界**。足した `.` がコメントの中に入るため |

上の表は計画どおりのアルゴリズムを JS で再現して全件照合した（2026-09-11、23 件一致）。
当初「ヒントなし」に分類していた複数行の関数呼び出しは、**始まりの行に足すと悪化する**という
最初の実験を読み違えたもので、終わりの行に足せば正しく直る本物のピリオド抜けだった。

## 厳しい判定の損得（Gate2 M2 で実測）

Q1 の厳しい判定は「件数が減れば採用」に比べて、得るものも失うものも小さい。数を書いておく。

- **止めた誤ヒント: 2 件**（58 入力中）。どちらも JavaScript の貼り付け — `console.log('a')` と
  `console.log('a');`。1 行に 2 エラーあり、ピリオドを足すと 1 に減るので、件数だけなら
  「ピリオド抜け」と言ってしまう
- **上の表の「ヒントなし」の残り 7 件は、件数だけの判定でも黙る。** 厳しい判定がそれらを守っているわけではない
- **捨てる本物の修正: 1 件**（M1 を直した後）。`WRITE 'a';` ⏎ `WRITE 'b';` ⏎ `WRTE 'd'.` —
  abaplint が 2〜4 行を 1 つのエラーにまとめるので、綴り間違いの行も対象になり、書き換え後に残る
  そのエラーで不採用になる。テストで「届かない形」として固定する

それでも厳しい判定を採るのは、誤ヒントの害（JavaScript を貼った人に「ピリオドを忘れた」と言い切る）が、
ヒントが出ない害（今と同じ）より大きいから。Q4 でヒントを言い切りにした根拠でもある。

## lint が止まる時間（Q6 / Q7 が守るもの）

**手段 A を入れても、探索中にワーカーが塞がることは消えない。** `parseAsync` はイベントループに譲らないと実測で確定した
（1,502 ms のパース中にマクロタスク 0 回）。探索の間、タイピングで積まれた `lint` は 1 件も動けず、エディタの下線が更新されない。

だから 16 kB（Q6）と 3 秒（Q7）は残す。**ただし守るものが変わった。**

| | 旧（手段を替える前） | 新 |
|---|---|---|
| 上限が守るもの | 本物の構文エラーを `stalled` にしない | 探索中に `lint` が止まる時間 |
| 上限を超えたとき | **`outcome` が嘘になる**（`syntax_error` → `stalled`） | ヒントが 1 個出ない／エディタの下線が遅れる |
| 合格線 | 最悪 5 秒未満、超えたら人へ戻す | **撤回**。実測して PR に書くが、ゲートにしない |

**正直に書く数字**: 打ち切りは「次の再パースを始めない」しかできず、始まったパースは止められない。
16 kB の重い形（`x⏎` × 8,192 行）では **元のパース 1.5 秒 ＋ 予算 3 秒 ＋ 始まってしまった候補 1 回 5.8 秒 ＝ 約 10 秒**。
上限は停止時間を**縮める**が**保証しない**。それでよいと判断したのは、超えて壊れるのが `lint` の応答だけで、
`outcome` は壊れないから。Gate2 が 3 周つぶした「上限で時間を抑えきれない」は、この差し替えで high ではなくなる。

### 大きさの上限を 16 kB にした根拠（Gate2 H1 / 3 周目 H-B の実測、据え置き）

**パースの重さは文字数に比例しない。** 1 回のパース（Node、2 回のうち速い方）:

| 1 行の中身を並べた形 | 16 kB | 32 kB | 64 kB |
|---|---|---|---|
| `lv = \|a#\| && 'b' "c";`（全体が 1 文） | 111 ms | 369 ms | 1,151 ms |
| `WRITE 'value#';`（全体が 1 文） | 116 ms | 315 ms | 1,431 ms |
| `console.log("x");` | 37 ms | 66 ms | 122 ms |
| `WRTE 'a'.`（行ごとにエラー） | 24 ms | 38 ms | 68 ms |
| `x⏎`（全体が 1 文） | 1,502 ms | **19,201 ms** | OOM |

同じ 16 kB でも形で 24 ms 〜 1.5 秒と 60 倍違う。64 kB では二重引用符の探索だけで Firefox 12.8 秒・WebKit 10.6 秒だった
（本番ビルドで実測）。16 kB は「形の差が残ることを承知で、停止時間を実用域に縮める」値であって、保証ではない。

採らなかった上限:

- **再パースした文字数の合計** — 非比例のため、同じ合計でも中身次第で時間が大きくずれる
- **経過時間だけ（大きさの上限なし）** — 64 kB では候補 1 回が形によって 2.6 秒あり、打ち切りの行き過ぎが大きい
- **上限をさらに下げる（8 kB など）** — 形の差は残るので保証にならず、200 行超の貼り付けからヒントが消える

失うもの: 16 kB（おおよそ 400 行）を超える貼り付けには、ヒントも `silent_loss` も付かない。
Run 1 回あたりの平均は約 20 行（GA4 2026-08-28..09-10、7,312 回）。

## 守ること（不変条件）

1. **打ち切りに達しない入力では、二重引用符の探索の結果は 1 件も変わらない** — 既存の `syntaxRepair.test.ts` は
   無修正で緑。**旧版の「16 kB 以下なら 1 件も変わらない」は取り下げる**: 打ち切りは重い形で候補の途中を切るので、
   16 kB 以下でも結果が変わりうる。`double_quote` の出方は #75 の出荷日をまたぐと、重い貼り付けのぶんだけ切れ目が入る
2. **ユーザーのソースは送らない** — 送るのは列挙値だけ。行番号も送らない（画面表示専用）
3. **Run の失敗時だけ**ヒントを探す。`lint` の経路では探さない。16 kB 超はどの探索もしない（成功側の `silent_loss` も）
4. **探索は `syntax_error` の判定を変えられない** — 判定はもう送信済みだから。**これは構造で保証される**ようになり、
   「候補の再パースが投げたらヒントなし」は保険として残す（判定を守るためではなく、追いかけの 1 通を必ず送るため）
5. **1 回の `transpile` 要求に対して、ワーカーは必ず 2 通返す。** 追いかけの 1 通が欠けると、親は `run_result` を
   20 秒待ってから送ることになる（壊れはしないが遅れる）
6. **`run_click` と `run_result` は 1:1 のまま。** 送るのが遅れるだけで、落とさない。落ちうるのは
   「追いかけを待っている間にタブを閉じた Run」だけ
7. **`duration_ms` の意味を変えない** — `endRun` が呼ばれた時点で確定させ、追いかけ待ちを足さない
8. **`stalled` は追いかけを待たない。** ワーカーが答えないという判定そのものなので、待てば 20 秒足して送ることになり、
   取りこぼしの窓が倍になる。`stalled` はその場で送る
9. **変わることを 1 つ受け入れる**: トランスパイル中に Stop を押した Run は、いままで `silent_loss` が付かなかったが、
   これからは追いかけを待つあいだに探索が終わるので値が付きうる。`CLAUDE.md` が挙げる「absence の原因」から
   「トランスパイル前の Stop」が減る。データは増える方向なので受け入れ、文書を直す
10. `syntax_key` / `syntax_statement` / 表示されるエラーメッセージは今までどおり `errors[0]` から
11. ヒントの文言は作者が書いた固定文。Tailwind のユーティリティ名になる英単語を裸で書かない（#44）

## やらないこと

- **#76（元のパースそのものの重さ）** — 別 PR（Q12）。`x⏎` の形で 32 kB 19 秒、64 kB で Node が OOM。手段 A は効かない
- **新しい GA4 パラメータ・イベント** — 登録が要り、登録前のデータは遡及しない（Q10）
- 「打ち切った」と「見つからなかった」を GA4 で区別すること（新しいパラメータが要る）
- 二重引用符の判定を厳しくすること（2026-09-08 以降のデータと比べられなくなる）
- エラーが出ない側のピリオド／セミコロン（実測でどちらも必ずエラーになる）
- エディタへ修正を自動で当てること、Validator モードへの配線
- ほかの記法（`//` コメント、`==`、`{ }` など）
- 16 kB を超える貼り付けへのヒント（Q6）

### e2e が新しく証明しなければならないこと

`abaplintWorker.ts` と `App.tsx` には単体テストが無い（#17）ので、プロトコルの変更は e2e が唯一の証拠になる。

1. **判定が先に出ること** — 16 kB の重い形（`x⏎` × 8,192）を貼って Run し、`stopped responding` が出ずにエラーが表示される。
   これが手段 A の効き目そのもの。**時間の合格線は先に測ってから置く**: 同じ入力の「元のパース 1 回」をそのブラウザで測り、
   その 2 倍を上限とする（元のパースがそのまま判定までの時間だから）。これを超えるなら遅いのは探索ではなく**元のパース**で、
   それは #76 の領域 — 上限の値を動かさず人へ戻す（Q12）
2. **ヒントが後から届いて継ぎ足されること** — `WRITE 'a';` で `semicolon`、`WRITE: 'a',` ⏎ `'b'` で `missing_period`
3. **ヒントが「出ない」こと**（`console.log('a')` の貼り付け）— **エラーが見えただけでは証拠にならない**。
   いまはエラーとヒントが同じ更新で決まるので不在が同時に確定していたが、A のあとヒントは後から来る。
   `data-search`（Q13）が `pending` から `done` に変わるまで待ってから、ヒントが無いことを確かめる（#70 の教訓）
4. **既存の e2e 4 件が同じ理由で無効になるので、同じ足場で直す** — `syntaxHint.spec.ts` の否定 2 件、
   `silentLoss.spec.ts` の `a correct program that prints nothing gets no hint`（プレースホルダが出た時点では
   `silent-loss` がまだ届いていない）と `a partly eaten chain still prints what survived`（出力の表示と
   ヒントの到着の順序が保証でなくなる）。`helpers.ts` の `waitForRunToEnd` の説明文も偽になる
   （「ヒントは transpile result と一緒に届く」が成り立たなくなる）
4. **配線を外すと赤になること** — 変異は型が通る形で入れ、`run_in_background` で 1 回だけ走らせ、
   `✘` と `✓` を別々に数える（Gate2 H2 / H-A）
