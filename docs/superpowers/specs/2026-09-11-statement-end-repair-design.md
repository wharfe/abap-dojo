# ピリオド抜け・行末セミコロンに直し方を出す（#67 の残り 2 形）

Gate1（grilling による軽量版）。2026-09-11 に Q1〜Q5 をユーザーが確定。Q6 は Gate2 1 周目の指摘 H1 を受けて同日に追加で確定。Q7 は Gate2 3 周目の指摘 H-B を受けて同日に追加で確定。

## 何を解決するか

#69 の出荷後（2026-09-09..10）、`syntax_statement = WRITE` の `parser_error` 31 件のうち、
直し方のヒントが出たのは二重引用符の 4 件だけだった。残りの大半は #67 が見つけた未対応の 2 形
— **文末のピリオド抜け**と**行末のセミコロン**。どちらも abaplint のメッセージは
`Statement does not exist in the configured ABAP version` で、何を直せばよいかを言わない。

## 既にある仕組みを探したか

探した。abaplint はこれらの `parser_error` に修正案を付けない（`getDefaultFix()` /
`getAlternativeFixes()` はどちらも `null`、2026-09-11 実測）。ピリオドやセミコロンを扱う
ルールも無い（`ArtifactsRules` のキーを検索）。したがって #69 の方式 —
**行の見た目で判断せず、書き換えた版を abaplint に再パースさせ、判定が良くなった書き換えだけ採る** —
をそのまま再利用する（`src/workers/syntaxRepair.ts`）。

## 決めたこと

| # | 決定 |
|---|---|
| Q1 | 新しい 2 種は**厳しい判定**で採用する: エラー件数が減り、**かつ対象にしたエラーの行範囲から始まるエラーが 1 つも残っていない**。二重引用符の判定（件数が減れば採用）は変えない |
| Q2 | `syntax_repair` の値を 2 つ足す: `missing_period` / `semicolon`。新しいパラメータではないので GA4 の登録は不要 |
| Q3 | 1 行ずつの候補に加え、「対象の行をまとめて直す」候補も入れる。まとめ候補が勝ったときは行番号を言わない |
| Q4 | ヒントは条件付きにせず言い切る（厳しい判定がその根拠） |
| Q5 | 試す順は 二重引用符 → セミコロン → ピリオド抜け。最初に見つかった時点で止める。種類ごとに最大 10 候補 + まとめ候補 1 |
| Q6 | 探索する大きさの上限を 64 kB → **16 kB** に下げ、既存の二重引用符・`silent_loss` の探索にも同じ値で効かせる（#75 を同じ PR で直す）。再パース文字数の合計による上限は入れない（下の「所要時間と大きさの上限」） |
| Q7 | 16 kB に加えて、**Run ごとに探索全体で共有する 3 秒の打ち切り**を入れる。探索を始めてから 3 秒を過ぎたら新しい再パースを始めず、ヒントなし（`silent_loss` は「探索未完了」＝送らない）で終える。大きさだけでは時間を保証できないため（Gate2 3 周目 H-B） |

## 候補の作り方（2026-09-11 の実測に基づく）

候補は**元のエラーの行範囲**（`getStart().getRow()`〜`getEnd().getRow()`）からだけ作る。

- **semicolon**: 範囲内で `;`（後ろの空白・`\r` は可）で終わる行の `;` を `.` に置き換える。
  1 行ずつ + 全エラーの該当行をまとめて
- **missing_period**: エラーの**終わりの行**の末尾に `.` を足す（始まりの行に足すと、
  複数行にまたがる文で 1→2 に悪化する）。まとめ候補は範囲内で `.` `,` `:` で終わらない
  空でない行すべてに足す（`,` `:` を除くのはチェーンの継続行を壊さないため）
- **まとめ候補の「対象」**は、書き換えた行を含むエラーだけ。別の行の無関係なエラーは書き換えても
  必ず残るので、対象に入れると本物の修正を捨てる（Gate2 M1。`WRITE 'a'` ⏎ `WRITE 'b'` ⏎
  `WRITE 'c'.` ⏎ `WRTE 'd'.` が黙っていた）

| 入力 | 期待 |
|---|---|
| `WRITE 'hello'`（最終行 / 途中 / IF の中） | `missing_period`、行番号あり |
| `WRITE: 'a',` ⏎ `'b'`、`lv = to_upper(` ⏎ `'a' )`（複数行の文の末尾） | `missing_period`、終わりの行 |
| 2〜3 行連続のピリオド抜け | `missing_period`、行番号なし |
| `WRITE 'a';` / 2 行連続 / CRLF | `semicolon`（1 行は行番号あり / 2 行は行番号なし） |
| `WRTE 'a'.` / `console.log('a')` / `console.log('a');` / `const x = 5;` / `let x = 1` ⏎ `console.log(x)` / `print('a')` / ピリオド抜け + 別行の綴り間違い / `DATA lt TYPE string_table.` | **ヒントなし** |
| `WRITE 'a' " note`（行末コメントに隠れたピリオド抜け） | **ヒントなし — 届かない限界**。足した `.` がコメントの中に入るため |

上の表は計画どおりのアルゴリズムを JS で再現して全件照合した（2026-09-11、23 件一致）。
当初「ヒントなし」に分類していた複数行の関数呼び出しは、**始まりの行に足すと悪化する**という
最初の実験を読み違えたもので、終わりの行に足せば正しく直る本物のピリオド抜けだった。

## 厳しい判定の損得（Gate2 M2 で実測）

Q1 の厳しい判定は「件数が減れば採用」に比べて、得るものも失うものも小さい。数を書いておく。

- **止めた誤ヒント: 2 件**（58 入力中）。どちらも JavaScript の貼り付け — `console.log('a')` と
  `console.log('a');`。1 行に 2 エラーあり、ピリオドを足すと 1 に減るので、件数だけなら
  「ピリオド抜け」と言ってしまう
- **上の表の「ヒントなし」の残り 7 件は、件数だけの判定でも黙る。** 厳しい判定がそれらを守っているわけではない
- **捨てる本物の修正: 1 件**（M1 を直した後）。`WRITE 'a';` ⏎ `WRITE 'b';` ⏎ `WRTE 'd'.` —
  abaplint が 2〜4 行を 1 つのエラーにまとめるので、綴り間違いの行も対象になり、書き換え後に残る
  そのエラーで不採用になる。テストで「届かない形」として固定する

それでも厳しい判定を採るのは、誤ヒントの害（JavaScript を貼った人に「ピリオドを忘れた」と言い切る）が、
ヒントが出ない害（今と同じ）より大きいから。Q4 でヒントを言い切りにした根拠でもある。

## 所要時間と大きさの上限（Q6、Gate2 H1 で実測）

**パースの重さは文字数に比例しない。** 二重引用符やセミコロンがどの行でもピリオドを食う貼り付け
（LLM が `WRITE "a".` を並べた形）はファイル全体が 1 つの文になり、1 回のパースが
`WRITE 'value#';` を並べた形で 16 kB 116 ms・64 kB 1,431 ms（Node）— 文字数 4 倍で約 12 倍、形によっては約 38 倍。行ごとにエラーが切れる形はほぼ比例
（64 kB で 68 ms）。

そのため旧上限の 64 kB では、二重引用符の探索だけで Firefox 12.8 秒・WebKit 10.6 秒かかり
（本番ビルドで実測）、後ろに新しい探索が 22 回続くと 20 秒のウォッチドッグを超える。超えると
本物の `syntax_error` が `stalled`（エンジンが応答しない）として表示・計測される（#75）。
16 kB では同じ 12 回が 3 エンジンとも 1 秒未満で、3 種合わせた最悪 34 回でも数秒に収まる見込みだった（下のとおり、形によっては外れた）。

**16 kB だけでは足りなかった（Gate2 3 周目 H-B、実測）。** 形による重さの差は、大きさを揃えても残る。
16 kB の `foo(1);` を並べた形は元のパース 1 回が 512 ms（`WRITE 'value#';` の 4 倍強）で、1 行ずつの候補も 1 文のまま同じ重さなので、
探索が Node で 4.9〜6.5 秒、`foo(1, "x");` では 7.8 秒かかった。測っていない形はもっと重いかもしれない。

そこで Q7: **探索全体で共有する 3 秒の打ち切り**を足す。

- 打ち切りは「次の再パースを始めない」だけで、始まったパースは止められない。最悪は **元のパース + 3 秒 + 候補 1 回分**。
  16 kB の候補 1 回は既知の最悪で約 0.5 秒（Node）なので、20 秒のウォッチドッグに対して十分な余裕がある
- 期限は Run ごとに 1 つ。失敗側は二重引用符 → セミコロン → ピリオドの 3 種で共有し、成功側の `silent_loss` は自分の 1 つを持つ
- 仕組みは再パース関数を包むだけ（期限を過ぎたら投げる）。既存の探索は再パースが投げたら「ヒントなし／探索未完了」を返す作りなので、
  探索関数そのものは変えない。その約束が崩れないよう、3 つの探索それぞれについてテストで固定する
- 3 秒の根拠: 普段の貼り付け（Run 1 回あたり平均約 20 行）の探索は数百 ms 以内で終わり、発動しない。16 kB の重い形でも候補の半分以上は試せる
- **払うもの**: 打ち切りが発動するほど重い貼り付けでは、同じコードでも端末の速さでヒントの有無が変わる。`syntax_repair` が無いことは
  「探して見つからなかった」と「打ち切った」を区別しない（区別するには新しいパラメータと GA4 の登録が要る — やらないこと）。
  `silent_loss` は既存の「探索未完了 = 送らない」に入る

採らなかった上限:

- **再パースした文字数の合計** — 上の非比例のため、同じ合計でも中身次第で時間が大きくずれる（64 kB の 1 回のパースが形によって 68〜2,642 ms）
- **経過時間だけ（大きさの上限なし）** — 64 kB では候補 1 回が形によって 2.6 秒（Node）あり、打ち切りの行き過ぎが大きい
- **16 kB のまま基準を緩める** — もっと重い形があれば、本物のエラーが `stalled` に化ける
- **上限をさらに下げる（8 kB など）** — 形の差が残るので保証にならず、200 行超の貼り付けからヒントが消える

失うもの: 16 kB（おおよそ 400 行）を超える貼り付けには、ヒントも `silent_loss` も付かない。
Run 1 回あたりの平均は約 20 行（GA4 2026-08-28..09-10、7,312 回）。`double_quote` と `silent_loss` の出方が
16〜64 kB の入力でだけ変わるので、#75 の出荷日をまたぐ比較には小さな切れ目が入る。
大きさの上限だけでは「測っていない、もっと重い形」を守れない。Q7 の打ち切りはそのための備え。

## 守ること（不変条件）

1. **16 kB 以下のソースでは、二重引用符の探索の結果は 1 件も変わらない** — 既存の `syntaxRepair.test.ts` は
   無修正で緑（16〜64 kB は Q6 で探さなくなる。既存の大きさのテストは 64 kB 超の入力なので影響しない）
2. **ユーザーのソースは送らない** — 送るのは列挙値だけ。行番号も送らない（画面表示専用）
3. **Run の失敗時だけ**探す。`lint` の経路では探さない。16 kB 超はどの探索もしない（成功側の `silent_loss` も）
4. 候補の再パースが投げたら**ヒントなし**で終わり、`syntax_error` の判定は変えない
5. `syntax_key` / `syntax_statement` / 表示されるエラーメッセージは今までどおり `errors[0]` から
6. ヒントの文言は作者が書いた固定文。Tailwind のユーティリティ名になる英単語を裸で書かない（#44）
7. **探索は Run ごとの期限（3 秒）を過ぎたら新しい再パースを始めない**。打ち切られた探索は、ヒントなし・`silent_loss` を送らない、で終わり、
   `syntax_error` の判定は変えない

## やらないこと

- エラーが出ない側（`silent_loss`）— 実測でピリオド抜けもセミコロンも必ずエラーになる
- 二重引用符の判定を厳しくすること（9/8 以降のデータと比べられなくなる）
- エディタへ修正を自動で当てること、Validator モードへの配線
- ほかの記法（`//` コメント、`==`、`{ }` など）
- 16 kB を超える貼り付けへのヒント（Q6）
- 「打ち切った」と「見つからなかった」を GA4 で区別すること（新しいパラメータと登録が要る。Q7）

加えて、**上限ちょうど（16 kB）の最悪ケースの所要時間**を実装後に Node と 3 ブラウザで実測して PR に書く。
入力は上の「所要時間と大きさの上限」で重いと分かった、ファイル全体が 1 つの文になる形。
`foo(1);`・`foo(1, "x");` を含む各形で、Node の「元のパース + 探索」（3 回の中央値）が 5 秒未満、ブラウザで Run から
エラー表示までが 6 秒未満であること（期限 3 秒 + 候補 1 回分 + 元のパース）。期限そのものは時計を差し替えた単体テストで、
期限を過ぎた後に再パースが呼ばれないことと、3 つの探索がそれぞれ「答えなし」で終わることを確かめる。
超えたら上限の値を変えずに人へ戻す。300 行の貼り付け（旧版の見積もり 413 ms）は最悪ケースではなかった。
