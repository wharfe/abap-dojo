# ピリオド抜け・行末セミコロンに直し方を出す（#67 の残り 2 形）

Gate1（grilling による軽量版）。2026-09-11 に Q1〜Q5 をユーザーが確定。

## 何を解決するか

#69 の出荷後（2026-09-09..10）、`syntax_statement = WRITE` の `parser_error` 31 件のうち、
直し方のヒントが出たのは二重引用符の 4 件だけだった。残りの大半は #67 が見つけた未対応の 2 形
— **文末のピリオド抜け**と**行末のセミコロン**。どちらも abaplint のメッセージは
`Statement does not exist in the configured ABAP version` で、何を直せばよいかを言わない。

## 既にある仕組みを探したか

探した。abaplint はこれらの `parser_error` に修正案を付けない（`getDefaultFix()` /
`getAlternativeFixes()` はどちらも `null`、2026-09-11 実測）。ピリオドやセミコロンを扱う
ルールも無い（`ArtifactsRules` のキーを検索）。したがって #69 の方式 —
**行の見た目で判断せず、書き換えた版を abaplint に再パースさせ、判定が良くなった書き換えだけ採る** —
をそのまま再利用する（`src/workers/syntaxRepair.ts`）。

## 決めたこと

| # | 決定 |
|---|---|
| Q1 | 新しい 2 種は**厳しい判定**で採用する: エラー件数が減り、**かつ対象にしたエラーの行範囲から始まるエラーが 1 つも残っていない**。二重引用符の判定（件数が減れば採用）は変えない |
| Q2 | `syntax_repair` の値を 2 つ足す: `missing_period` / `semicolon`。新しいパラメータではないので GA4 の登録は不要 |
| Q3 | 1 行ずつの候補に加え、「対象の行をまとめて直す」候補も入れる。まとめ候補が勝ったときは行番号を言わない |
| Q4 | ヒントは条件付きにせず言い切る（厳しい判定がその根拠） |
| Q5 | 試す順は 二重引用符 → セミコロン → ピリオド抜け。最初に見つかった時点で止める。種類ごとに最大 10 候補 + まとめ候補 1 |

## 候補の作り方（2026-09-11 の実測に基づく）

候補は**元のエラーの行範囲**（`getStart().getRow()`〜`getEnd().getRow()`）からだけ作る。

- **semicolon**: 範囲内で `;`（後ろの空白・`\r` は可）で終わる行の `;` を `.` に置き換える。
  1 行ずつ + 全エラーの該当行をまとめて
- **missing_period**: エラーの**終わりの行**の末尾に `.` を足す（始まりの行に足すと、
  複数行にまたがる文で 1→2 に悪化する）。まとめ候補は範囲内で `.` `,` `:` で終わらない
  空でない行すべてに足す（`,` `:` を除くのはチェーンの継続行を壊さないため）

| 入力 | 期待 |
|---|---|
| `WRITE 'hello'`（最終行 / 途中 / IF の中） | `missing_period`、行番号あり |
| `WRITE: 'a',` ⏎ `'b'`、`lv = to_upper(` ⏎ `'a' )`（複数行の文の末尾） | `missing_period`、終わりの行 |
| 2〜3 行連続のピリオド抜け | `missing_period`、行番号なし |
| `WRITE 'a';` / 2 行連続 / CRLF | `semicolon`（1 行は行番号あり / 2 行は行番号なし） |
| `WRTE 'a'.` / `console.log('a')` / `console.log('a');` / `const x = 5;` / `let x = 1` ⏎ `console.log(x)` / `print('a')` / ピリオド抜け + 別行の綴り間違い / `DATA lt TYPE string_table.` | **ヒントなし** |
| `WRITE 'a' " note`（行末コメントに隠れたピリオド抜け） | **ヒントなし — 届かない限界**。足した `.` がコメントの中に入るため |

上の表は計画どおりのアルゴリズムを JS で再現して全件照合した（2026-09-11、23 件一致）。
当初「ヒントなし」に分類していた複数行の関数呼び出しは、**始まりの行に足すと悪化する**という
最初の実験を読み違えたもので、終わりの行に足せば正しく直る本物のピリオド抜けだった。

## 守ること（不変条件）

1. **二重引用符の探索の結果は 1 件も変わらない** — 既存の `syntaxRepair.test.ts` は無修正で緑
2. **ユーザーのソースは送らない** — 送るのは列挙値だけ。行番号も送らない（画面表示専用）
3. **Run の失敗時だけ**探す。`lint` の経路では探さない。64 kB 超は探さない
4. 候補の再パースが投げたら**ヒントなし**で終わり、`syntax_error` の判定は変えない
5. `syntax_key` / `syntax_statement` / 表示されるエラーメッセージは今までどおり `errors[0]` から
6. ヒントの文言は作者が書いた固定文。Tailwind のユーティリティ名になる英単語を裸で書かない（#44）

## やらないこと

- エラーが出ない側（`silent_loss`）— 実測でピリオド抜けもセミコロンも必ずエラーになる
- 二重引用符の判定を厳しくすること（9/8 以降のデータと比べられなくなる）
- エディタへ修正を自動で当てること、Validator モードへの配線
- ほかの記法（`//` コメント、`==`、`{ }` など）
